Where the Operations Console is — and why you can't see it

It exists. It lives inside the app you already have, at #/console. It is hidden on purpose, and it opens only for a signed-in account holding one specific grant. You do not need to launch separate apps to see it.

The console opens only when all three are true:

1. The account service is configured in the build you're using (cloudConfigured).

2. You are signed in.

3. Your account holds a live console:operate grant at platform scope, in role_grants.

Miss any one and the screen shows a single sentence and stops. It is also deliberately absent from every menu a student sees: lib/nav.ts lists it as a nested screen "offered from nothing a student sees".

1. What the repository actually contains

The audit in the repo (OPS-CONSOLE-DISCOVERY-AUDIT.md, 3 Oct) found a substantial, security-first console foundation. Since then, more workspaces have landed. The console screen is app/src/screens/Console.tsx; its navigation contract is app/src/lib/console/workspaces.ts.

3. Do you need separate apps?

No, not now. Keep one repository, one set of shared platform services, and three surfaces:

SurfaceWhere it lives todaySplit later only if
Public company sitecompany-site/ and app/src/site/It already has its own build
Education app (student, faculty, advisor, institution)app/Not needed
Semester Operationsapp/ at #/consoleYou need independent releases, stronger staff-only auth, or network restrictions, and have a team to run another deployable

A separate app would add login callbacks, configuration and deployments. It would not make any hidden screen appear.

4. How to open it, step by step

  1. On a development or staging environment, never production first, apply the Supabase migrations, including the console ones.
  2. Run the app from app/ with the account-service environment variables set. The audit lists the build and test commands; read app/package.json for the exact local-start script.
  3. Create two test accounts: one operator and one ordinary student.
  4. Give the operator a console:operate grant at platform scope, through the repo's existing role-grant mechanism (see supabase/rolegrants.check.sql for the grant shape: scope, expiry, audited grantor). Add one domain grant, for example tenant:implement for one school, to see a domain workspace.
  5. Sign in as the operator and open <your local address>/#/console. The context bar should show the environment, your identity, your grants and MFA freshness.
  6. Sign in as the student and open the same address. It must show the notice, and calling the console functions directly must be refused by the database.

I didn't run any of this. Script names, environment-variable names and the local port come from the repo's files, and you need to confirm them there.

5. The smallest change that makes it discoverable

Add an Operations entry, shown only to accounts that hold the grant, to the account menu or workspace switcher. Use the same check the console already makes (holdsConsole(grants), fed by loadMyCapabilities()). Students never see it. Navigation stays a convenience; the database still decides access.

Interactive mock of this entry and the real gate: ui_kits/console-entry.

Then pick one complete flow to prove end to end. Support is the strongest candidate: list → case detail → assign or change status → saved → refresh shows the result and its audit entry. Its UI, tests and migrations already exist; its build flag is the remaining switch.
